Run your own Farcaster client

A Snapchain read node you own, and a client that reads from it — in three commands. No API keys, no hosted data provider, nobody's rate limit.

Quickstart

git clone https://github.com/webthethird/snapstart && cd snapstart

./snapstart provision      # 0. furnish the compute
./snapstart node up        # 1. start a Snapchain read node
./snapstart client create  # 2. issue an app key and launch the client

That is the whole thing. The rest of this page explains what each command does, what the protocol is doing underneath, and the ways it can go wrong — all of which we hit while building it.

Before you start the node, check the clock. Step 1 takes 8–12 hours, and Snapchain replaces its snapshots daily while deleting the previous ones. A restore that runs past a rotation fails — and fails in a way that leaves you with a node that looks healthy and silently refuses to post.

Start step 1 between 05:20 and 21:00 UTC. See Timing for why.

What you are actually building

If you have run an Ethereum node, you already understand this. You can read chain data from Alchemy with an API key and a rate limit, or you can run Reth yourself and query localhost with nobody's permission. Farcaster has the same split: Neynar is Alchemy, and a Snapchain read node is your own Reth.

EthereumFarcaster
Reth / Geth full nodeSnapchain read node — stores all state, serves queries, cannot propose blocks
ValidatorSnapchain validator — permissioned, gated on a key in a registry contract
eth_sendRawTransactionsubmitMessage
eth_syncingGET /v1/info
EOA private keyCustody key — owns the account
Session keyApp key — scoped, expiring, revocable

You cannot run a validator: the validator set lives in a contract on Ethereum mainnet and you are not in it. That is fine. A read node stores the full state and serves every read API, which is everything a client needs.

Three identities, not one

Farcaster splits what Ethereum keeps together:

LayerWhat it isCryptography
FIDYour account numberNone — it is a uint256 in a registry contract
Custody addressOwns the FIDsecp256k1, from your seed phrase
App keySigns your postsEd25519, generated per client

An app key is a session key. Your custody key is the EOA that owns the account; the app key is a scoped delegate you hand to a client so it can act without holding the keys to everything. One account can have many — Warpcast holds one, your client holds another, and revoking one does not touch the rest.

That is also why a cast can tell you which client posted it. The signature identifies the software, not just the person, which is what makes filtering by client possible at all.

0. Provision the compute

./snapstart provision

Four API calls and a boot script. An SSH keypair dedicated to this node, a firewall, an instance, and a disk — then cloud-init installs Docker. Nothing mystical.

Defaults to AWS. Hetzner is about a third the price but cannot complete a restore on a new account: its default volume quota is 1024 GB and the restore peaks above that. Verified by probe — a resize to 1030 GB is refused. Use SNAPSTART_PROVIDER=hetzner if your quota has been raised.

New AWS accounts land on the Free Plan, which cannot run this. The Free Plan refuses any instance type that is not free-tier eligible, and the largest eligible type is 2 vCPU / 8 GiB where Snapchain needs 4 / 16. No quota increase fixes it — you have to upgrade to a paid plan. Credits still apply.

Only one credential, and the node never sees it

The cloud API key belongs to the provisioning script, not to the node. provision, status and destroy need it; node and client do not. Once the node is running it holds no credentials of any kind — no RPC endpoint, no data provider, nothing to sign up for.

1. Start the read node

./snapstart node up

This installs upstream's snapchain.sh, writes its config without prompting, and starts the node. It then restores from a snapshot — which is the slow part, and the part with teeth.

Timing, and why it matters

Restoring takes 8–12 hours. The docs say "up to 2 hours"; we measured 8h14m on one run and over 12 on another.

Snapchain regenerates each shard's snapshot daily and deletes the previous one. The restore fetches a manifest once at the start, then downloads shards in order. If a shard's snapshot is replaced before the restore reaches it, every chunk request returns 404 and the node panics.

Each shard rotates at a different time of day:

shard 0   05:18 UTC
shard 2   08:03 UTC
shard 1   13:16 UTC

Which is why there is no safe fixed ordering, and why the practical advice is simply: start between 05:20 and 21:00 UTC. Outside that window the restore crosses a rotation.

The failure is silent, which is what makes it dangerous. After the panic, Docker restarts the node. It finds a non-empty database, concludes it is already bootstrapped, and starts serving — with one shard missing.

It then answers every read correctly, reports hundreds of millions of messages, and rejects every write with unknown fid, because app-key registration routes to the shard that never restored. Nothing in the logs or /v1/info says so.

Check readiness properly

./snapstart node ready

This is the check that matters. "The API responds" and "the database has data" are both true of a broken node. node ready verifies every shard is present and within 100 blocks of the tip, and fails explicitly if shard 0 is missing. 

  shard           height          delay          messages  state
  0             49007206              1                 0  ok
  1             49007206              1         458606290  ok
  2             48842741              1         455621742  ok

  ready: all shards present and within 100 blocks of the tip

Shard 0 holds no user messages, which is exactly why a message-count check would call a broken node healthy.

2. Create the client

./snapstart client create

This asks for your seed phrase, uses it once to authorize an app key, and then forgets it. From that point the client holds only the app key.

About that seed phrase

Use a throwaway account. Not one you care about.

A client holding an app key can post as you. A client holding your seed phrase can transfer your account away, change its recovery address, and spend anything in the custody wallet. Those are not the same risk.

Registering a fresh account costs about $0.20 — the docs say $10, but IdGateway.price() currently returns roughly 0.0001 ETH, which includes the first storage unit. There is no good reason to test with an account that matters.

More generally: only paste a seed phrase into software whose source you have read, from people you have reason to trust. That includes this project. The relevant code is scripts/app-key.ts — it is about 140 lines and worth the three minutes.

Where a flow supports delegated signer authorization instead of a seed phrase import, prefer it. This tutorial imports a phrase because the exercise is to issue a key with nothing else in the loop, not because it is the right pattern for a production client.

What issuing an app key actually does

Registering a key used to require an Optimism transaction. Under FIP-272 it does not: you submit a KEY_ADD message authorized by an EIP-712 signature from your custody address. No gas, no transaction.

Three signatures are involved, which is the part that trips people up:

  1. a SignedKeyRequest — the requesting app saying "I asked for this key"
  2. a KeyAdd signature from your custody address, authorizing the key, its scopes and its lifetime
  3. the message envelope itself, signed by the new key — proof that whoever submits it actually holds it

The key is deliberately limited:

ScopesOnly the message types the client sends. A key scoped to casting cannot follow anyone.
TTL90 days, sliding — it refreshes on use, so abandoned keys expire by themselves.
NonceStrictly increasing per account, so an old authorization cannot be replayed.

If you are writing this yourself: the gasless EIP-712 domain is { name: "Farcaster KeyAdd", version: "1", chainId: 1 } with no verifyingContract. It sits beside near-identically named onchain helpers — signKeyRequest vs signGaslessKeyRequest — and they are not interchangeable. Using the wrong one produces a signature that verifies locally and is rejected by the network.

Also: deadline is in Farcaster seconds (epoch 2021-01-01), not Unix seconds.

Writes are confirmed, not assumed

A node returns 200 once your message is well-formed and handed to the gossip layer — and then discards what happens next. A node with no peers logs InsufficientPeers, drops your cast, and still returns 200.

So the client never trusts the status code. It knows the message hash before submitting, and polls until the node reports it back. Blocks are about a second apart, measured at the tip, so confirmation normally takes a few seconds; after 20 it reports honest failure rather than claiming success.

Do not post immediately after starting your node. It needs gossip peers first, and until it has them your writes vanish with a 200.

Filtering by the client that posted

Every cast carries the Ed25519 key that signed it. That key's registration records the FID of the app that requested it, and that FID has a profile with a name: 

cast.signer  →  the key's registration  →  requestFid  →  that app's name

Posting through Warpcast means Warpcast's key signed your cast. So a feed can be filtered by the software that produced it: 

feed: 60 casts from 23 authors

   45  warpcast
   13  fireflyapp
    1  greg
    1  unknown client

include ["warpcast"] -> 45
exclude ["warpcast"] -> 15

That output is from a real feed on a real node. Some casts are legitimately unattributable — keys registered before the metadata existed, or self-issued keys with no app behind them. Those render as unknown client and are never silently dropped; a filter that hides posts because a lookup failed is a bug that looks like a feature.

It names what it is about to delete, then verifies the resources are actually gone before discarding local state — and keeps that state if anything survived, so you can retry rather than being told you have stopped paying when you have not.

When it goes wrong

Every entry here is something we hit. Most are not in any documentation.

The node serves reads but every post fails with unknown fid

A shard did not restore. KEY_ADD routes to shard 0 unconditionally, and the block engine there needs your account's registration record — so with shard 0 missing, every write fails, for every account, including long-established ones.

The confusing part is that everything else works. /v1/validateMessage will tell you the same message is valid, because it checks structure rather than shard state.

Confirm with ./snapstart node ready. If a shard shows a delay in the millions it never restored, and it will not recover on its own — ours was closing at ~390 blocks/min against a 49.5 million block deficit, which is about 85 days. Wipe and re-bootstrap inside the timing window.

The restore panicked with a 404

Failed to download .rocks.snapshot/shard-0/chunk_0001.bin: HTTP 404
thread 'main' panicked at src/main.rs:422

The snapshot it was downloading got replaced and deleted mid-restore. Start again inside the timing window. Note that restarting without wiping does not fix it: the node sees a non-empty database and skips the snapshot entirely.

provision fails: "not eligible for Free Tier"

Your AWS account is on the Free Plan, which refuses instance types large enough to run Snapchain. Upgrade to a paid plan in Billing. Credits still apply.

resource_limit_exceeded on Hetzner

New Hetzner accounts cap volume storage at 1024 GB, below what the restore peaks at. Request an increase, or use AWS.

/v1/info returns nothing

Normal for the first several hours. The node does not serve until the restore completes, so the obvious health check reads as "broken" for most of a day. Watch ./snapstart node status instead.

Posts return 200 but never appear

The node accepted your message and failed to gossip it — most likely it has no peers yet. Wait a few minutes after startup. This is why the client confirms by reading back rather than trusting the status code.

Permission denied deleting node data

The container writes as root. On AWS you log in as ubuntu, so cleanup needs sudo. On Hetzner you are already root and never see this.

Honest limitations

Things worth knowing before you spend a day on this:

  • The restore is 8–12 hours and there is no resume. An interruption means starting over.
  • It needs 2 TB of disk at peak for a database that settles around 557 GB, because the snapshot staging is not reclaimed until the end. We proposed a fix.
  • Writing through someone else's validator is not an option — they require authentication. Your own read node is the only keyless write path.
  • This is a tutorial client, not a product. It reads a feed, posts, follows, reacts and filters by source client. It is not trying to be Warpcast.
