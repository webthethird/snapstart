Run your own Farcaster client

A Snapchain read node you own, and a client that reads from it — in three commands. No API keys, no hosted data provider, nobody's rate limit.

Quickstart

git clone https://github.com/webthethird/snapstart && cd snapstart

./snapstart provision      # 0. furnish the compute
./snapstart node up        # 1. start a Snapchain read node
./snapstart client create  # 2. issue an app key and launch the client

That is the whole thing. The rest of this page explains what each command does, what the protocol is doing underneath, and the ways it can go wrong — all of which we hit while building it.

Before you start the node, check the clock. Step 1 takes 8–12 hours, and Snapchain replaces its snapshots daily while deleting the previous ones. A restore that runs past a rotation fails — and fails in a way that leaves you with a node that looks healthy and silently refuses to post.

Start step 1 between 05:20 and 21:00 UTC. See Timing for why.

What you are actually building

If you have run an Ethereum node, you already understand this. You can read chain data from Alchemy with an API key and a rate limit, or you can run Reth yourself and query localhost with nobody's permission. Farcaster has the same split: Neynar is Alchemy, and a Snapchain read node is your own Reth.

EthereumFarcaster
Reth / Geth full nodeSnapchain read node — stores all state, serves queries, cannot propose blocks
ValidatorSnapchain validator — permissioned, gated on a key in a registry contract
eth_sendRawTransactionsubmitMessage
eth_syncingGET /v1/info
EOA private keyCustody key — owns the account
Session keyApp key — scoped, expiring, revocable

You cannot run a validator: the validator set lives in a contract on Ethereum mainnet and you are not in it. That is fine. A read node stores the full state and serves every read API, which is everything a client needs.

Three identities, not one

Farcaster splits what Ethereum keeps together:

LayerWhat it isCryptography
FIDYour account numberNone — it is a uint256 in a registry contract
Custody addressOwns the FIDsecp256k1, from your seed phrase
App keySigns your postsEd25519, generated per client

An app key is a session key. Your custody key is the EOA that owns the account; the app key is a scoped delegate you hand to a client so it can act without holding the keys to everything. One account can have many — Warpcast holds one, your client holds another, and revoking one does not touch the rest.

That is also why a cast can tell you which client posted it. The signature identifies the software, not just the person, which is what makes filtering by client possible at all.

0. Provision the compute

./snapstart provision

Four API calls and a boot script. An SSH keypair dedicated to this node, a firewall, an instance, and a disk — then cloud-init installs Docker. Nothing mystical.

Defaults to AWS. Hetzner is about a third the price but cannot complete a restore on a new account: its default volume quota is 1024 GB and the restore peaks above that. Verified by probe — a resize to 1030 GB is refused. Use SNAPSTART_PROVIDER=hetzner if your quota has been raised.

New AWS accounts land on the Free Plan, which cannot run this. The Free Plan refuses any instance type that is not free-tier eligible, and the largest eligible type is 2 vCPU / 8 GiB where Snapchain needs 4 / 16. No quota increase fixes it — you have to upgrade to a paid plan. Credits still apply.

Only one credential, and the node never sees it

The cloud API key belongs to the provisioning script, not to the node. provision, status and destroy need it; node and client do not. Once the node is running it holds no credentials of any kind — no RPC endpoint, no data provider, nothing to sign up for.

1. Start the read node

./snapstart node up

This installs upstream's snapchain.sh, writes its config without prompting, and starts the node. It then restores from a snapshot — which is the slow part, and the part with teeth.

Timing, and why it matters

Restoring takes 8–12 hours. The docs say "up to 2 hours"; we measured 8h14m on one run and over 12 on another.

Snapchain regenerates each shard's snapshot daily and deletes the previous one. The restore fetches a manifest once at the start, then downloads shards in order. If a shard's snapshot is replaced before the restore reaches it, every chunk request returns 404 and the node panics.

Each shard rotates at a different time of day:

shard 0   05:18 UTC
shard 2   08:03 UTC
shard 1   13:16 UTC

Which is why there is no safe fixed ordering, and why the practical advice is simply: start between 05:20 and 21:00 UTC. Outside that window the restore crosses a rotation.

The failure is silent, which is what makes it dangerous. After the panic, Docker restarts the node. It finds a non-empty database, concludes it is already bootstrapped, and starts serving — with one shard missing.

It then answers every read correctly, reports hundreds of millions of messages, and rejects every write with unknown fid, because app-key registration routes to the shard that never restored. Nothing in the logs or /v1/info says so.

Check readiness properly

./snapstart node ready

This is the check that matters. "The API responds" and "the database has data" are both true of a broken node. node ready verifies every shard is present and within 100 blocks of the tip, and fails explicitly if shard 0 is missing. 

  shard           height          delay          messages  state
  0             49007206              1                 0  ok
  1             49007206              1         458606290  ok
  2             48842741              1         455621742  ok

  ready: all shards present and within 100 blocks of the tip

Shard 0 holds no user messages, which is exactly why a message-count check would call a broken node healthy.
